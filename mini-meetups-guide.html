فكرة المشروع

منصة صغيرة شبه لوما: حد بيعمل meetup، والناس بتحجز فيه. أي يوزر ممكن يبقى منظم للـ meetups بتاعته، وحاجز في meetups غيره.

المنظم · Organizer

بيعمل meetup (العنوان، والمكان، والميعاد، وعدد الأماكن)، وبيقرر الحجز يحتاج موافقته ولا يتأكد على طول. ولو محتاج موافقة، هو اللي بيوافق أو يرفض.

الحاجز · Attendee

بيتصفح الـ meetups الجاية ويحجز مكان. يقدر يلغي الحجز، ويرجع يحجز تاني بعدين.

مثال لـ flow كامل

  1. هاجر عملت meetup اسمه "Laravel Cairo": 50 مكان، ومحتاج موافقة.
  2. علي حجز، فحجزه بقى pending ومش ماسك مكان لسه.
  3. هاجر وافقت، فالحجز بقى confirmed واتحسب من الـ 50.
  4. علي مش هيقدر يروح، فلغى. الحجز بقى cancelled والمكان فضي.
  5. علي غيّر رأيه وحجز تاني. نفس الـ row رجع pending، من غير ما نعمل حجز جديد.

قواعد البيزنس

كل قاعدة هنا ليها مكان في الكود بيطبّقها. لما تحتاجي تعدّلي سلوك، ابدئي من هنا.

الـ Meetups

  • المنظم بس يقدر يعدّل أو يحذف الـ meetup.
  • الميعاد لازم يكون في المستقبل (after:now).
  • الـ capacity أقل حاجة 1.
  • مينفعش تنزّلي الـ capacity لأقل من عدد الحجوزات المؤكدة.

الـ Bookings

  • المنظم مينفعش يحجز في الـ meetup بتاعه.
  • مينفعش تحجزي meetup بدأ خلاص.
  • حجز واحد بس لكل يوزر في كل meetup (unique).
  • محتاج موافقة؟ يبقى pending. مش محتاج؟ confirmed على طول.
  • المؤكد بس اللي بيتحسب من الـ capacity. فالتشييك بيحصل لحظة ما الحجز يتأكد.
  • الملغي يقدر يتفعّل تاني. المرفوض نهائي.

دورة حياة الحجز

ده الـ State Machine. كل سهم هو تحويل مسموح، وأي تحويل مش موجود بيرمي InvalidBookingTransitionException ويرجّع 422.

stateDiagram-v2
    [*] --> pending: book (approval)
    [*] --> confirmed: book (auto)
    pending --> confirmed: approve
    pending --> rejected: reject
    pending --> cancelled: cancel
    confirmed --> cancelled: cancel
    cancelled --> pending: re-book (approval)
    cancelled --> confirmed: re-book (auto)
    rejected --> [*]

confirmed✗—✗✓

ليه الملغي يرجع والمرفوض لأ؟

الإلغاء اليوزر عمله بنفسه، فمن حقه يغيّر رأيه. الرفض قرار المنظم. لو سمحنا بالرجوع، اليوزر هيفضل يبعت طلبات للمنظم كل شوية.

وليه confirmed ميروحش rejected؟ المنظم لو قبل حد، مينفعش يرجع يرفضه بعدين. ده قرار بيزنس متطبق في الكود.

رحلة الـ Request

كل طبقة بتسأل سؤال واحد، ولو الإجابة "لأ" بترجّع status code مختلف. فالـ code لوحده بيقولك المشكلة فين.

Middlewareauth:sanctum: انت مين؟ · throttle: مش بتبعت كتير؟401 · 429
Route Binding{meetup} يتحول لـ Meetup::findOrFail()404
Form Requestauthorize(): مسموحلك؟ ← بعدها rules(): بياناتك صح؟403 · 422
ControllerGate::authorize() لو مفيش Form Request، وبعدين ينادي الـ Service403
Serviceقواعد البيزنس، والـ transactions، والـ locks422

المشكلة

enum BookingStatus: string {

الـ State Machine

المشكلة
من غير قواعد، أي status ممكن يتحوّل لأي status، فحجز مرفوض ممكن يرجع مؤكد.
الحل
allowedTransitions() في الـ enum بتحدد كل حالة تروح لفين، وtransitionTo() في الـ model هي الباب الوحيد اللي الـ status بيتغيّر منه.
public function transitionTo(BookingStatus $to): void
{
    if (! $this->status->canTransitionTo($to)) {
        throw new InvalidBookingTransitionException($this->status, $to);
    }
    $this->update(['status' => $to]);
}
تغيير الـ status يتم بس عن طريق transitionTo()، عمره ما يكون update(['status' => ...]) مباشر.

متضيفيش حاجة مش محتاجاها YAGNI

المشكلة
كل status زيادة معناه حالات أكتر في الكود والـ tests. وpending من غير موافقة منظم هيبقى dead state: الحجز يدخله ومحدش يطلّعه.
الحل
ضفنا pending لما بقى ليه سبب يخرج منه (المنظم يوافق أو يرفض). وماستخدمناش Spatie لأن كل القواعد عندنا ملكية.
أي status لازم يبقى ليه سبب يدخله وسبب يخرج منه.

الداتابيز آخر خط دفاع DB Constraints

المشكلة
لو جالنا requestين في نفس اللحظة، ممكن الاتنين يعدّوا التشييك اللي في الكود.
الحل
unique(user_id, meetup_id) بيمنع الحجز المكرر، وunsignedInteger بيمنع الـ capacity السالبة، وstatus من غير default عشان لو نسينا نحدده MySQL يضرب error.
خلي الغلط يظهر بصوت عالي. Error واضح أحسن من بيانات غلط بتدخل في صمت.

Status ولا Soft Delete؟

المشكلة
اليوزر لغى ورجع عايز يحجز تاني، والـ unique بيمنعه.
الحل
الـ soft delete مش بيمسح الـ row، فالـ unique لسه هيمنع. وكمان cancelled بيعبّر عن نفس المعنى. فبنفعّل نفس الـ row تاني عن طريق cancelled → pending/confirmed.
حالة البيزنس مكانها الـ status. الـ soft delete للبيانات اللي عايزين نخبيها ونقدر نرجّعها.

الـ Conventions بتفرق

المشكلة
كتبنا start_time في الـ migration وstarts_at في الـ model، والقيمة اتجاهلت من غير أي error.
الحل
أعمدة التاريخ بتنتهي بـ _at. والاسم لازم يبقى واحد في الـ migration والـ fillable والـ casts. وorganizer_id محتاج constrained('users') لأنه مش ماشي على شكل {model}_id.
// AppServiceProvider::boot()
Model::preventSilentlyDiscardingAttributes(! app()->isProduction());

وانتي بتطوّري، خلي Laravel يضرب error على أي حاجة بتتجاهل في صمت.

ثغرة IDOR Insecure Direct Object Reference

المشكلة
يوزر B عامل login، فيبعت PATCH /meetups/5 ويعدّل meetup بتاع A. أو يبعت POST /bookings/12/approve ويوافق على حجزه هو.
الحل

الـ Policies

هي إيه
class عادي فيه methods بترجّع true أو false. مش middleware. هي بتجاوب بس، واللي بيمنع هو اللي سألها.
بتتنده من
can: على الـ route، أو authorize() في الـ Form Request، أو Gate::authorize() في الـ controller، أو $user->can() في أي مكان.
public function update(User $user, Meetup $meetup): bool
{
    return $meetup->isOrganizedBy($user);
}
ليه منفصلة
update وdelete نفس الكود النهارده، بس هما قرارين مختلفين ممكن يتغيّروا لوحدهم. والتكرار الحقيقي اتشال في isOrganizedBy().
ليه بس 2
الـ index والـ show والـ store مسموحين لأي حد عامل login، فمفيش قاعدة نكتبها. ولو ناديتي ability مش موجودة، الـ default هو الرفض.
شيلي التكرار في الـ "إزاي"، وسيبي كل "قرار" لوحده.

Policy و Middleware و Spatie

الأداةبتسألتعرف الـ object؟مثال
Middlewareعن الـ request كلهلأعامل login؟ محظور؟
Policyعن حاجة معينةأيوهالـ meetup ده بتاعك؟
Spatieعن دورك (متخزن في الداتابيز)لأانت admin؟

Spatie مش بديل للـ Policy، هو بيكمّلها: $user->hasRole('admin') || $meetup->isOrganizedBy($user).

لو السؤال فيه "الحاجة دي بالذات"، يبقى Policy. لو عن الـ request أو اليوزر عمومًا، يبقى Middleware.

الـ Authorization قبل الـ Validation

المشكلة
لو الـ Policy في الـ controller، يوزر B يبعت capacity: 5 فياخد 422 "must be at least 30"، ويعرف عدد الحجوزات المؤكدة.
الحل
authorize() في الـ Form Request بتشتغل قبل rules()، فـ B ياخد 403 على طول.
public function authorize(): bool
{
    return $this->user()->can('update', $this->route('meetup'));
}
return true معناها "مسموح للكل". و$this->route('meetup') بتاخد اسم الـ parameter ({meetup})، مش اسم الـ route (meetups.update).
مسموحلك؟ الأول. بياناتك صح؟ بعدين.

Sanctum Tokens

إزاي
Login يرجّع token، والـ frontend يبعته في Authorization: Bearer .... الـ token متخزن hashed، والـ plain text بيظهر مرة واحدة بس.
الاسم
createToken('api'): الـ 'api' ده label بس، مفيد عشان تفرّقي بين الأجهزة. والـ logout بيمسح الـ token الحالي بس.
الـ login
رسالة واحدة للإيميل الغلط والباسورد الغلط، عشان محدش يعرف مين مسجل (User Enumeration). وعليه throttle:5,1 ضد الـ Brute Force.

تصميم الـ API

إيه اللي يدخل، وإيه اللي يطلع

الـ Form Requests

ليه
الـ controller يركز على الـ logic، والـ validation في مكانها. ولو فشلت، Laravel يرجّع 422 قبل ما يدخل الـ controller.
مهم
$request->validated() بترجّع اللي عدّى بس، فمحدش يقدر يبعت organizer_id أو is_admin. والـ rules ممكن تبقى dynamic، زي min:{$minCapacity}.
أي حاجة تعرفيها من الـ token (زي المنظم)، متاخديهاش من الـ request أبدًا.

Route Model Binding

إزاي
/meetups/{meetup} مع Meetup $meetup: Laravel يجيبه لوحده، ولو مش موجود يرجّع 404.
الفخ
User $user على route مفيهوش {user} بيدّيكي new User() فاضي من غير error. استخدمي $request->user() لليوزر اللي عامل login.

الـ API Resources

ليه
whitelist: أي عمود جديد في الداتابيز مش هيطلع إلا لو ضفتيه. وعقد ثابت مع الـ frontend.
إزاي
whenLoaded() وwhenCounted() وwhen() بيطلّعوا الـ key بس لو الـ controller جهّز البيانات. والـ fn () => معناها lazy evaluation، يعني القيمة متتحسبش غير لو الشرط صح.
'spots_left' => $this->whenCounted('confirmedBookings',
    fn ($count) => $this->capacity - $count),
'organizer'  => new UserResource($this->whenLoaded('organizer')),
الـ Controller يقرر يجيب إيه، والـ Resource يعرض اللي اتجاب. الـ Resource عمره ما يعمل query.

المشكلة

الحل

الـ API بيتكلم بلغة البيزنس ("وافق"، "الغي")، مش بلغة الداتابيز ("غيّر الـ status").

الأداء والـ Architecture

الكود يفضل سريع ومتنظم وهو بيكبر

مشكلة N+1 و Eager Loading

المشكلة

الحل
with('user') قبل ما البيانات تتجاب، أو load('user') على حاجة اتجابت خلاص، فتبقى 2 queries. وwithCount() بتحسب جوه نفس الـ query.

load()الـ modelبعد ما اتجاب (approve)

والـ string ('user') هو اسم الـ method بتاعة العلاقة في الـ model. وorganizedMeetups() بالقوسين = relation تقدري تضيفي عليها شروط، ومن غير قوسين = النتايج نفسها.

الـ Race Condition و lockForUpdate

المشكلة
فاضل مكان واحد، وسارة وعلي حجزوا في نفس الملّي ثانية. الاتنين قروا "49 من 50"، فالاتنين اتحجزلهم.
الحل
نقفل الـ meetup جوه transaction، فالحجوزات على نفس الـ meetup تمشي واحد ورا التاني.
DB::transaction(function () {
    $meetup = Meetup::whereKey($id)->lockForUpdate()->firstOrFail();
    // SELECT ... FOR UPDATE  →  الباقي يستنى
    $booking->refresh();   // أحدث نسخة بعد الانتظار
    // count  →  create / confirm
});
لاحظي
الـ lock بيشتغل جوه transaction بس. والعلاقات ($booking->meetup) مبتعرفش تعمل lock. وrefresh() بيحدّث نفس الـ object، أما fresh() فبيرجّع object جديد.
أي قرار بيعتمد على حالة في الداتابيز، لازم يتاخد على بيانات اتقرت بعد الـ lock.
